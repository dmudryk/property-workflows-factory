## Research findings

**Already in main (vendor-db, `20261109000000_vendor_role.sql`):**
- `profiles_role_check` allows `vendor`.
- `private.is_staff` accepts vendors, so a vendor can be an assignee.
- `private.staff()` returns nothing to a vendor.
- `launch_run` is limited to manager and admin. AC-VENDOR-01, 02, 06, 07 and 09 are already marked "реалізовано".
- `private.can_see_run` already lets an assignee see the run, so a vendor sees `runs` rows where they have a task.
- `mark_task_done` already allows the assignee, so AC-VENDOR-05 needs no SQL change.

**Gaps behind the five red tests:**
- **RLS on `run_tasks`.** `run_tasks_select_visible` (`20261020123813_runs_launch.sql:167`) uses only `can_see_run(run_id)`. A vendor therefore sees all 5 tasks of the run, which breaks AC-VENDOR-04 and the progress and email rules. The fix is a new migration with a later timestamp. It drops and recreates the policy as `can_see_run(run_id) AND (current_app_role() <> 'vendor' OR assignee_id = auth.uid())`. This keeps `can_see_run` and leaves managers and admins unchanged.
- **Hidden-data check.** The vendor already sees only their own `profiles` row, and `list_staff` returns nothing to them (test 04 filters out the vendor's own email). Template RLS for vendors still needs checking. Test 08 expects empty `templates`, `template_versions` and `template_drafts` for a vendor. If any policy lets a vendor through, the same migration must tighten it.
- **`src/lib/runs/rules.ts`.**
  - `Role` is `"manager" | "admin"`; add `"vendor"`.
  - Add `yourTasksLabel(tasks, userId)`, which returns `Your tasks: N of K done`.
- **`src/lib/auth/actor.ts`.** `requireActor` builds the actor only for manager or admin (line 23), so a vendor gets `actor = null`. Add `vendor` there.
- **`src/lib/auth/roles.ts`.** Add `canSeeTemplates(actor)`: true for manager and admin, false for vendor and null.
- **`src/lib/runs/list-view.ts`.** Add `runsEmptyState(vendor)` with the exact texts from the contract.
- **Pages, all currently unaware of vendors:**
  - `/runs` always shows the "Launch a template" action. Its select also pulls `template_name` and a whole-run progress count, which for a vendor would count only their own tasks.
  - `/runs/[id]` shows the template name and version, the run manager and the whole-run progress. It also shows each task's assignee email.
  - `/templates` and `/templates/[id]` have no role check. Only `new`, `edit` and `versions` use `NotEnoughRights`, and only for non-admins.
  - `/runs/new` has no role check.
  - `SidebarNav` hard-codes the "Templates" item.
- **`NotEnoughRights`.** Its default `backHref` is `/templates`, which is wrong for a vendor. It needs `backHref="/runs"`.
- **`docs/conformance.md`.** Rows 105, 106, 107, 110 and 112 have «Код» as "—" and status "відкладено".

## Design

- **Defence in depth.** The database is the authority. RLS limits a vendor's `run_tasks` rows, and the pages additionally branch on `actor.role === "vendor"`.
- **Role before data.** Every guarded page calls `requireActor()` and checks the role before any query runs.
- **Vendor run view.** Use a dedicated read path: select only `id, case_name, status` from `runs`, and select tasks without `assignee_id` display. Don't call `list_staff`, and don't render the template name, version, manager or progress. Pass an `assigneeLabel` of "" or hide that element. The existing `RunTasks` component gets a `vendor` flag that hides the assignee line and shows `yourTasksLabel` instead of `progressLabel`.
- **`canMark`.** For a vendor, `canMarkDone` already holds for their own tasks, since the actor id equals the assignee. This relies on the actor no longer being null.
- **Nav.** Pass `role` into `SidebarNav` from `AppShell` (it already receives `user.role`) and filter items with `canSeeTemplates`. `SidebarNav` is a client component, so pass a plain boolean prop rather than the actor.

## Risks

- **`requireActor` change.** It turns `actor = null` into a real vendor. Anywhere that treated `null` as "no role" (`canManageTemplates`, `canMark`) still works, but check the server actions in `runs/actions.ts` and `templates/actions.ts`. The `markDone` action must not reject vendors on the TS side.
- **Policy recreation.** If it is not written as drop then create, the migration fails. The `private.current_app_role()` name is assumed from `can_see_run`, so confirm it exists before using it.
- **Progress leaking.** `progressCounts` and `progress` on `/runs` would show "N of M" for a vendor with M equal to their own task count, which looks like whole-run progress. Replace it with `yourTasksLabel`, not a reworded variant.
- **Email leaking.** `staffLabel` falls back to "—", but make sure the vendor branch never calls `list_staff` and never renders the assignee line.
- **Hidden scenarios.** I can't see these. Hidden UAT likely covers `/runs/new` and `/templates/[id]` for vendors, and the Templates nav item, so don't stop at the five visible tests.
- **Protected files.** Tests, scripts, openspec, requirements and `supabase/demo-users.json` can't be touched, so every fix has to go in product code or the new migration.
- **Test command limits.** Only `node scripts/factory-tap.mjs` and the vitest command are allowed. No pipes, redirects or chaining.
