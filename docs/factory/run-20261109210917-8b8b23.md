# Plan: Assign a vendor and let the vendor work on their own tasks

This task is database only: one new migration plus the `docs/conformance.md` rows. I changed no files.

## Research findings

- **Role set.** The current `profiles_role_check` allows `('manager','admin')`. It was last changed in `20261020123813_runs_launch.sql:7-10`, in the order drop check → data → default → new check. The default is `'manager'`.
- **Why the fixture fails today.** `vendor-fixtures.ts:addVendor` inserts into `auth.users`, so the trigger creates a profile with the default role. It then sets `role = 'vendor'` as service_role. Today the check constraint rejects that, so all five tests fail in their "Given" step.
- **`private.is_staff(uuid)`** (`20261020123813_runs_launch.sql:130`) accepts only manager and admin. `launch_run` uses it to validate assignees and raises `INVALID_ASSIGNEE`. The current `launch_run` is in `20261026175944_templates_versions.sql:328-400`, at line 377.
- **`launch_run` caller check** (line 348) already allows only `('manager','admin')`. A vendor therefore gets `NOT_ALLOWED` (42501) before any insert, and `manager_id` is always the caller. AC-VENDOR-09 should be satisfied without touching `launch_run`'s caller check.
- **`private.staff()` and `public.list_staff()`** were last defined in `20261021071209_runs_clarifications.sql:77-110`. Both return `(id, email)`.
  - Rows are filtered to `p.role in ('manager','admin')`.
  - The caller must be a manager or admin, otherwise no rows come back. A vendor already gets zero rows with no error.
  - Only the target-role filter needs to change.
- **`private.can_see_run`** shows a run to an admin, the run's manager, or the assignee of at least one task. A vendor sees only their own runs. AC-VENDOR-06 should already hold once V exists.
- **`private.mark_task_done`** (`20261020124103_runs_complete_tasks.sql:43`) allows the assignee, the run's manager, or an admin. A vendor on someone else's task gets `NOT_ALLOWED` and the task stays `to_do`. AC-VENDOR-07 should already hold.
- **Templates.** The select policies for templates, versions and drafts allow only `manager` and `admin`, with `admin` only for drafts. A vendor sees nothing.
- **Grants.** `authenticated` has only `select` on `runs` and `run_tasks`. No grant changes are needed.
- **Conformance rows.** `docs/conformance.md:103-111` has AC-VENDOR-01, 02, 06, 07 and 09 as "відкладено" with "—" in the «Код» column.

## Design

One new migration, `supabase/migrations/20261109000000_vendor_role.sql`. The timestamp must be later than `20261027124320`. It contains:

1. **Role set**, in the prescribed order:
   - `alter table public.profiles drop constraint profiles_role_check;`
   - no data update, because nothing is renamed
   - `alter column role set default 'manager';`
   - `add constraint profiles_role_check check (role in ('manager','admin','vendor'));`
2. **`private.is_staff` → assignable users.**
   - **Preferred option:** `create or replace private.is_staff` to include `'vendor'`. This is the smallest diff, and `launch_run` stays untouched, so the `create or replace` keeps the signature and grants.
   - **Risk:** `is_staff` may have other callers. Grep `src/` and the migrations before choosing.
   - **Alternative:** add `private.is_assignable(uuid)` and redefine `launch_run` with it. This is a bigger diff, and it would copy the whole function body.
3. **`private.staff()`.** Replace it with `create or replace`, keeping the same signature `(id, email)`.
   - The filter becomes `p.role in ('manager','admin','vendor')`.
   - The caller guard stays `in ('manager','admin')`, so a vendor gets no rows.
   - `public.list_staff()` is unchanged.
4. **Unchanged:** `can_see_run`, `mark_task_done`, the template policies and the grants. The tests assert these, so I leave them alone.
5. **Docs.** Fill «Код» for AC-VENDOR-01, 02, 06, 07 and 09 with the migration path. Set «реалізовано» only after `node scripts/factory-tap.mjs` shows the test green.

## Risks

- **`is_staff` has other callers.**
  - A caller that means "may launch" would wrongly admit a vendor.
  - The grep on role checks showed `launch_run` as the only `is_staff` caller. I did not search `src/` or the rest of the SQL.
  - Mitigation: confirm the caller list, and fall back to a separate `is_assignable` function if needed.
- **`list_staff` exposure.**
  - The output must stay `(id, email)` with no `role` or `full_name`.
  - Changing the return columns would force a drop and create, as in the clarifications migration.
  - Mitigation: keep the signature and change only the filter.
- **The new default role.**
  - The default must stay `'manager'`. A vendor default would give new users vendor rights, and the trigger-created profile in the fixture relies on the default being allowed by the constraint.
  - The demo-user script, `scripts/create-demo-users.mjs`, may need a vendor user. Scripts are out of scope here.
- **Existing assertions about the role set.** A test elsewhere may assert the exact role list or the `INVALID_ASSIGNEE` behaviour for a non-staff assignee. For example, an AC-RUN-04-style test could use a vendor as the "invalid" assignee. I can't check this without running the suite, so run the full vitest before finishing.
- **Migration order and PGlite.** The test harness applies the migrations in filename order, so the timestamp must sort last. The `20261109…` prefix does.
- **Vendor pages** are out of scope. Hidden scenarios may probe them, but this task covers only the database contract.
